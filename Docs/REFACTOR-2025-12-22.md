## ✅ Fix applied today: OpenAI key persistence on iPhone/TestFlight

### Problem
`ProcessInfo.processInfo.environment["OPENAI_API_KEY"]` works in some *developer* contexts but **does not exist on real iPhone builds / TestFlight**. That’s why you’ve seen:

> OPENAI_API_KEY not found in environment variables.

### What changed
- Added secure Keychain storage for the API key.
- Added an in-app Settings screen to save/clear the key.
- Updated the strategy engine + manager detection to read the key from Keychain (with env-var fallback for simulator/dev convenience).
- Removed verbose OpenAI payload logging that could include **base64 screenshot data**.

### Files changed / added
- Added `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/Support/OpenAIKeyStore.swift`
- Added `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/App/MineOpsSettingsView.swift`
- Updated:
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/Strategy/AIStrategyEngine.swift`
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/Strategy/AIStrategyPipeline.swift`
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/Strategy/OpenAIModels.swift`
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/App/CommandCenterViewV2.swift`
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/OCR/OCRReviewView.swift`
  - `MineOpsCompanionPackage/Sources/MineOpsCompanionFeature/Strategy/StrategyPipelineView.swift`

### Why this is the “correct” approach
- **You should not ship a personal OpenAI API key in the app bundle** (TestFlight or App Store).
- Each user/tester can input their own key.
- Keychain is the standard iOS solution for secrets.

## Clean code & architecture review

### Strengths
- Good separation by feature folders: `OCR/`, `Strategy/`, `Support/`, etc.
- Clear, incremental evolution: OCR → review → strategy pipeline.
- Good safeguards already landing in OCR:
  - SM-card validation (`SMCardValidator`) to reject non-game screenshots.
  - Duplicate detection via fingerprints.
  - “Import New” tracking by asset identifiers.

### High-value cleanup opportunities

#### 1) Avoid logging sensitive / huge payloads
**Found:** `ResponsesPayloadBuilder` was printing entire payload dictionaries, including `base64Image`.

**Why it matters:**
- huge logs → performance/memory issues
- screenshot content is personal data

**Status:** fixed today (only minimal debug messages remain).

#### 2) Two “strategy engines” = duplication risk
You have:
- `AIStrategyEngine` (network call + retry + cache)
- `AIStrategyPipeline` (CoreData caching + OpenAI vision detection + prompt building)
- `StrategyEngine` (local deterministic strategy generation)

**Risk:** repeated logic paths, inconsistent behavior, harder testing.

**Suggestion:** make one “strategy service” surface area:
- `StrategyService` protocol with two implementations:
  - `OpenAIStrategyService` (network)
  - `LocalStrategyService` (deterministic fallback)

This removes duplication and makes the UI layer simpler.

#### 3) MV vs MVVM drift
Project guidance says “MV pattern; no ViewModels”, but there are multiple `ObservableObject` view models.

**Suggestion (incremental):**
- keep `ObservableObject` for models/stores, but avoid “UI-only ViewModel” when it can be derived in the view.
- Start by deleting the smallest one (`StrategySummaryViewModel`) and inlining its logic into `StrategySummaryView`.

This is optional but aligns with your stated architecture rule.

#### 4) CoreData used for AI cache
CoreData is currently used for caching AI results.

**Suggestion:** for this use case (personal app, small data volume), consider:
- SwiftData (if you want a modern Apple-native persistence)
- or even JSON files / UserDefaults if the cache is truly ephemeral.

CoreData is not “wrong”, just a heavier dependency than needed.

## Recommended OCR refactor: build a structured “SM Card Model”

### Problem with the current approach
Current OCR mainly produces:
- free-form text fields
- loose regex-based extractions

That’s fine for a prototype, but equipment/elements require:
- **image-region analysis** (icons are not reliably OCR’d)
- stable, composable parsing stages

### Proposed pipeline (practical and testable)
1) **Card gating** (already exists): `SMCardValidator`
2) **Normalize OCR text** (one place): unify OCR cleanup rules
3) **Text extraction**
   - `SMNameParser`
   - `SMLevelParser` (level + promotion)
   - `SMScoreParser`
   - `SMRankParser` (stars + rank-up fraction)
   - `SMAbilityTextParser` (active/passive labels, durations, multipliers)
4) **Icon extraction** (image-based)
   - `SMElementDetector` (cropped element icon region → template match)
   - `SMEquipmentDetector` (3 equipment slot regions → template match)
5) **Stat computation**
   - `SMComputedStats` from base + equipment + element bonuses
6) **Merge/update** into your roster store (see next section)

### Why this works
- Each stage can have focused tests.
- Icon detectors can be improved without destabilizing text parsing.

## Re-import behavior (update only, don’t duplicate)

### Current state
`OCRReviewViewModel.merge()` merges by `RecognizedSM.identityKey` (directory id or resolved name) and overwrites the record while preserving `id` and `storedImageName`.

That already gets you *most* of “update existing or add new”.

### The big missing piece: preserve user edits
If you edit a manager manually, a re-import can overwrite your edits.

**Recommendation:** store user edits separately:
- `RecognizedSMOverrides` keyed by `identityKey`
- Apply overrides after OCR parse.

This turns re-import into:
- OCR updates raw facts
- your manual corrections persist

### Extra improvement: detect *what changed*
Add a diff summary:
- new managers
- updated managers (fields changed)
- unchanged

This will make the UX feel very “professional tool” rather than “wipe and replace”.

## Strategy builder: incorporate equipment + elements + computed stats

### Current state
Strategy prompt uses:
- manager name
- department
- mine context (prestige, max shaft, mine type)

It does **not** include:
- your actual active/passive numbers
- element/equipment bonuses

### Recommended approach
1) Compute a lightweight “strategy facts model”:
   - `StrategyManagerFacts`
     - `name`
     - `department`
     - `activeMultiplier`
     - `activeDuration`
     - `cooldown`
     - `passiveBonuses`
     - `elements`
     - `equipment`
     - `computedScore` (optional)
2) Include those in the prompt so GPT can reason with numbers.
3) Keep a “hard rules” validator (already present in prompt) and also validate responses locally.

### UX improvement
Give the user a clear “data completeness” indicator:
- “12/20 managers have equipment parsed”
- “8/20 managers have element parsed”

This helps users understand why a strategy may be weaker.

## App Store Connect / TestFlight readiness notes

### OpenAI key handling
For TestFlight, the current approach (user-entered API key in Settings) is correct.

### Privacy disclosure
Because screenshots are processed and may be sent to OpenAI for manager detection/strategy:
- document it in the app’s privacy policy
- disclose any data collection in App Store Connect

### Stability/performance risk items
- Avoid base64 logging (done)
- Consider limiting image sizes before any network/vision operations
- Ensure Photo library permission handling is robust and user-friendly
